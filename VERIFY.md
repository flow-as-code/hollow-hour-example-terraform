# VERIFY: what this approach relies on, and how we know

The Amazon Connect behaviors the hotline relies on are the same whichever
repository deploys it, and the TypeScript-first repository checked them
against live instances, most of them on its dev instance (us-west-2) only;
row S2 also ran on qa and prod (us-east-1). Its
[VERIFY.md](https://github.com/flow-as-code/hollow-hour-example-typescript/blob/main/VERIFY.md)
is the ledger for those, with the AWS documentation, the date and the
service's answer for each. The ones this repository's design depends on:

| TypeScript-first row | What it settled                                                                                                   | Where it shows here                                             |
| -------------------- | ----------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| C1                   | Connect refuses a Compare without `Transitions.NextAction`                                                        | every Compare sets `next`; `tests/flows.tftest.hcl`             |

an instance create while another was pending in the same Region
("Currently pending instance creation requests, if successfully executed,

What follows is what the Terraform-first approach adds. Status is
**docs-checked** (the documentation or the tooling's published contract
says it), **offline-checked** (shown by a plan or test here, which makes no
AWS call), **read YYYY-MM-DD** (a read-only AWS call), **sandbox-checked YYYY-MM-DD, Region** (observed on a live apply from this
repository), or **needs sandbox** (only a live apply can show it). No account id, instance id or
ARN appears in any row.

| T1  | Does Connect accept an instance whose `/aws/connect/<alias>` log group already exists, and write its flow logs there?      | The admin guide says the group "is created automatically" with the instance and does not say what happens when it exists. The module creates it first, with retention, so that a greenfield apply needs no import and a destroy removes it after the instance. The alternatives fail greenfield: a group created after the instance would collide with the one Connect made, and an import needs a known name and an existing group at plan time. If Connect refuses, `manage_flow_log_group = false` leaves the group to Connect and retention to one AWS CLI call (README.md, "If Connect refuses the log group"). Yes, observed: the dev apply created the group first and then the instance, which reached ACTIVE after 58 s with no error, and DescribeLogGroups showed exactly one `/aws/connect/<alias>` group, retention 14 days. A test contact run through `hh-hotline-main` (scenario S2) then wrote 61 flow-log events to that group, from `hh-hotline-main`, `hh-greeting-standard`, `hh-district-menu` and `hh-district-old-town`. `manage_flow_log_group` stays true by default. | sandbox-checked 2026-09-30, us-west-2 | https://docs.aws.amazon.com/connect/latest/adminguide/contact-flow-logs.html                                                                                             |
